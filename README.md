# День 13 — Состояние задачи (Task State Machine)

## Цель

Реализовать формализованное состояние задачи в виде конечного автомата — Task State Machine.

Агент должен понимать:

- какая задача выполняется;
- на каком этапе находится задача;
- какой шаг выполняется сейчас;
- какое действие ожидается следующим;
- находится ли задача на паузе.

Также состояние должно сохраняться между запусками программы, чтобы работу можно было продолжить без повторного объяснения контекста.

---

- Python
- Google Gemini API
- `google-genai`

# Task State Machine

Для управления задачей используется конечный автомат:

```text
planning
    ↓
execution
    ↓
validation
    ↓
done
```

Каждое состояние имеет определённое назначение.

### planning

Планирование задачи.

На этом этапе определяется:

- что необходимо сделать;
- какой будет план;
- какие действия потребуются.

### execution

Выполнение задачи.

Агент работает над конкретными шагами реализации.

### validation

Проверка результата.

На этом этапе проверяется, правильно ли выполнена задача.

### done

Задача завершена.

Дальнейших действий не требуется.

---

# Формализованное состояние задачи

Состояние хранится в структуре:

```json
{
  "task": "Разработать Android-приложение для склада",
  "stage": "execution",
  "current_step": "Реализовать экран списка товаров",
  "expected_action": "Написать ViewModel",
  "paused": false
}
```

Основные поля:

| Поле | Назначение |
|---|---|
| `task` | текущая задача |
| `stage` | текущий этап |
| `current_step` | текущий шаг |
| `expected_action` | ожидаемое следующее действие |
| `paused` | находится ли задача на паузе |

Таким образом, состояние задачи хранится отдельно от обычного текста диалога.

---

# Переходы между состояниями

Разрешённые переходы определены явно:

```python
TRANSITIONS = {
    "planning": "execution",
    "execution": "validation",
    "validation": "done",
    "done": None
}
```

Получается последовательность:

```text
START
  ↓
planning
  ↓
execution
  ↓
validation
  ↓
done
```

Команда:

```text
next
```

переводит задачу на следующий этап.

Например:

```text
planning -> execution
```

Затем:

```text
execution -> validation
```

И:

```text
validation -> done
```

Из состояния `done` дальнейший переход невозможен.

---

# TaskStateMachine

Логика управления состоянием вынесена в отдельный класс:

```text
TaskStateMachine
```

Он отвечает за:

- создание новой задачи;
- хранение состояния;
- загрузку состояния;
- изменение текущего шага;
- переход между этапами;
- постановку задачи на паузу;
- продолжение задачи;
- сброс состояния.

AI-модель не решает самостоятельно, какой переход разрешён.

Этим управляет конечный автомат.

---

# Хранение состояния

Состояние задачи сохраняется в:

```text
task_state.json
```

После каждого изменения выполняется сохранение.

Например:

```text
start
↓
save()

next
↓
save()

pause
↓
save()

resume
↓
save()
```

При следующем запуске программы состояние загружается обратно.

```text
Запуск программы
       ↓
TaskStateMachine
       ↓
load()
       ↓
task_state.json
       ↓
восстановленное состояние
```

# Создание задачи

Для создания новой задачи используется:

```text
start <задача>
```

Например:

```text
start Разработать Android-приложение для склада
```

Автомат устанавливается в состояние:

```text
stage = planning
```

Также создаются начальные значения:

```text
current_step =
Определить план выполнения задачи

expected_action =
Сформировать план
```

---

# Текущий шаг

Помимо общего этапа задача содержит конкретный текущий шаг.

Используется команда:

```text
step <текущий шаг> | <ожидаемое действие>
```

Например:

```text
step Определить архитектуру приложения | Выбрать архитектуру
```

После этого состояние содержит:

```text
stage:
planning

current_step:
Определить архитектуру приложения

expected_action:
Выбрать архитектуру
```

Таким образом, `stage` показывает общий этап, а `current_step` — конкретную работу внутри этого этапа.

---

# Подключение состояния к Gemini

Task State автоматически передаётся модели при каждом обычном запросе.

Схема:

```text
TASK STATE
    +
USER MESSAGE
    ↓
  GEMINI
    ↓
  ANSWER
```

Например, пользователь спрашивает:

```text
Что мы сейчас должны сделать?
```

А Gemini получает:

```json
{
  "task": "Разработать Android-приложение для склада",
  "stage": "execution",
  "current_step": "Реализовать экран списка товаров",
  "expected_action": "Написать ViewModel",
  "paused": false
}
```

Поэтому пользователю не требуется заново объяснять состояние задачи.

---

# Pause

Задачу можно поставить на паузу на любом этапе:

```text
pause
```

Например:

```text
Этап:
execution

Текущий шаг:
Реализовать экран списка товаров

Ожидаемое действие:
Написать ViewModel

Статус:
PAUSED
```

При этом этап и текущий шаг не теряются.

Изменяется только:

```json
"paused": true
```

Если после этого спросить:

```text
Что мне делать дальше?
```

агент получает информацию о том, что задача приостановлена.

---

# Resume

Для продолжения используется:

```text
resume
```

При этом агент восстанавливает:

- этап;
- текущий шаг;
- ожидаемое действие.

Например:

```text
Задача продолжена.

Этап:
execution

Текущий шаг:
Реализовать экран списка товаров

Ожидаемое действие:
Написать ViewModel
```

Пользователю не требуется повторно описывать задачу.

---

# Продолжение после перезапуска

Одна из основных проверок — полное завершение программы во время выполнения задачи.

Например:

```text
execution
    ↓
pause
    ↓
exit
```

Состояние уже сохранено:

```text
task_state.json
```

После нового запуска:

```text
py main.py
```

программа выполняет:

```text
load()
```

и восстанавливает состояние.

Получаем:

```text
Задача:
Разработать Android-приложение для склада

Этап:
execution

Текущий шаг:
Реализовать экран списка товаров

Ожидаемое действие:
Написать ViewModel

Статус:
PAUSED
```

После:

```text
resume
```

работу можно продолжить с того же места.

# Сценарий тестирования

Создание задачи:

```text
start Разработать Android-приложение для склада
```

Проверка:

```text
state
```

Настройка текущего шага:

```text
step Определить архитектуру приложения | Выбрать архитектуру
```

Переход к выполнению:

```text
next
```

Результат:

```text
planning -> execution
```

Установка конкретного шага:

```text
step Реализовать экран списка товаров | Написать ViewModel
```

Проверка:

```text
state
```

Пауза:

```text
pause
```

После этого состояние сохраняется.

Завершаем программу:

```text
exit
```

Запускаем снова:

```text
py main.py
```

Состояние автоматически восстанавливается.

Продолжаем:

```text
resume
```

После этого можно спросить:

```text
Что мне делать дальше?
```

Агент использует сохранённый Task State без повторного объяснения задачи.

# Завершение State Machine

После выполнения переходим к проверке:

```text
next
```

```text
execution -> validation
```

После проверки:

```text
next
```

```text
validation -> done
```

Финальное состояние:

```text
stage:
done

current_step:
Задача завершена

expected_action:
Никаких действий не требуется
```

# Результат

В результате реализован AI-агент с формализованным состоянием задачи.

Агент умеет:

- хранить текущую задачу;
- хранить этап выполнения;
- хранить текущий шаг;
- хранить ожидаемое действие;
- выполнять контролируемые переходы между этапами;
- ставить задачу на паузу;

- восстанавливать состояние после перезапуска;
- передавать Task State в каждый запрос Gemini;
- продолжать работу без повторного объяснения задачи.

# Вывод

Обычная история сообщений отвечает на вопрос:

```text
О чём мы разговаривали?
```

Память агента отвечает:

```text
Что агент знает?
```

А Task State Machine отвечает на другой вопрос:

```text
Где мы сейчас находимся
в процессе выполнения задачи?
```

Формализованное состояние:

```text
TASK
+
STAGE
+
CURRENT STEP
+
EXPECTED ACTION
+
PAUSED
```

позволяет отделить состояние процесса от текста диалога.

Это делает поведение агента более предсказуемым и позволяет остановить выполнение задачи, сохранить состояние и продолжить работу позже без повторного объяснения контекста.
