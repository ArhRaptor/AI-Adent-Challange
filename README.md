# День 15 — Контролируемые переходы состояний

## Цель

Реализовать контролируемый жизненный цикл задачи с явными состояниями, разрешёнными переходами и условиями перехода.

Ассистент не должен иметь возможности:

- перепрыгивать обязательные этапы;
- начинать реализацию до утверждения плана;
- переходить к проверке до завершения реализации;
- завершать задачу без успешной валидации;
- менять состояние задачи во время паузы.

---

## Технологии

- Python
- Google Gemini API
- `google-genai`
- модель `gemini-3.5-flash-lite`
- JSON
- Finite State Machine
- Controlled State Transitions
- CLI

# Жизненный цикл задачи

Для задачи определены четыре допустимых состояния:

```text
planning
    ↓
execution
    ↓
validation
    ↓
done
```

Каждый этап имеет своё назначение:

| State | Назначение |
|---|---|
| `planning` | подготовка и утверждение плана |
| `execution` | выполнение реализации |
| `validation` | проверка результата |
| `done` | завершённая задача |

---

# Разрешённые переходы

Разрешённые переходы явно описаны в коде:

```python
ALLOWED_TRANSITIONS = {
    "planning": ["execution"],
    "execution": ["validation"],
    "validation": ["done"],
    "done": []
}
```

Таким образом, нельзя произвольно изменить состояние.

Например:

```text
planning → execution
```

разрешён.

Но:

```text
planning → validation
```

запрещён, потому что этап `execution` нельзя пропустить.

А переход:

```text
execution → done
```

тоже запрещён, поскольку обязательна `validation`.

---

# Условия переходов

Одного разрешённого перехода недостаточно.

Для перехода также должно быть выполнено соответствующее условие.

Используются три контрольных флага:

```json
{
  "plan_approved": false,
  "implementation_completed": false,
  "validation_passed": false
}
```

Полный жизненный цикл:

```text
planning
    │
    │ plan_approved = true
    ↓
execution
    │
    │ implementation_completed = true
    ↓
validation
    │
    │ validation_passed = true
    ↓
done
```

---

# Утверждение плана

На этапе:

```text
planning
```

переход к:

```text
execution
```

запрещён, пока:

```text
plan_approved = false
```

Попытка выполнить:

```text
goto execution
```

должна быть заблокирована с объяснением:

```text
Нельзя начать execution:
план ещё не утверждён.
```

Для утверждения плана используется:

```text
approve plan
```

После этого:

```text
plan_approved = true
```

и переход:

```text
planning → execution
```

становится доступным.

---

# Завершение реализации

После перехода в:

```text
execution
```

нельзя сразу перейти к:

```text
validation
```

Для этого сначала должна быть завершена реализация:

```text
implementation_completed = true
```

Используется команда:

```text
complete implementation
```

После этого разрешается:

```text
execution → validation
```

---

# Валидация

На этапе:

```text
validation
```

задачу нельзя сразу перевести в:

```text
done
```

Необходимо сначала подтвердить успешную проверку:

```text
validation_passed = true
```

Используется:

```text
pass validation
```

Только после этого разрешается:

```text
validation → done
```

---

# Два уровня контроля перехода

Перед изменением состояния выполняются две проверки.

## 1. Проверка графа

Сначала проверяется, существует ли такой переход вообще.

Например:

```text
planning → validation
```

не существует в:

```python
ALLOWED_TRANSITIONS
```

поэтому переход блокируется.

## 2. Проверка условия

Даже если переход существует:

```text
planning → execution
```

он не будет выполнен без:

```text
plan_approved = true
```

Общая схема:

```text
REQUEST TRANSITION
        ↓
Переход разрешён графом?
       / \
     НЕТ  ДА
      ↓    ↓
   BLOCK  Выполнено условие?
             / \
           НЕТ  ДА
            ↓    ↓
         BLOCK  TRANSITION
```

---

# Метод validate_transition()

Вся проверка выполняется до изменения состояния:

```python
validate_transition(target_state)
```

Метод проверяет:

1. существует ли запрошенное состояние;
2. находится ли задача на паузе;
3. разрешён ли переход из текущего состояния;
4. выполнены ли необходимые условия.

Если хотя бы одна проверка не проходит:

```text
ПЕРЕХОД ЗАБЛОКИРОВАН
```

и текущее состояние остаётся прежним.

---

# Явный переход

Для тестирования реализована команда:

```text
goto <state>
```

Например:

```text
goto validation
```

позволяет специально попытаться перейти в произвольное состояние и проверить защиту State Machine.

Это удобно для демонстрации запрещённых переходов.

---

# Переход к следующему этапу

Для нормального прохождения жизненного цикла используется:

```text
next
```

Команда определяет разрешённое следующее состояние и передаёт переход в тот же механизм проверки.

Таким образом, `next` не обходит правила State Machine.

---

# Проверка перепрыгивания этапа

Создаём новую задачу:

```text
reset
start Разработать Android-приложение для склада
```

Текущее состояние:

```text
planning
```

Пробуем:

```text
goto validation
```

Такой переход должен быть заблокирован:

```text
planning → validation
```

не входит в список разрешённых переходов.

---

# Проверка перехода без утверждения плана

Находясь в:

```text
planning
```

выполняем:

```text
goto execution
```

Сам переход:

```text
planning → execution
```

разрешён графом.

Но:

```text
plan_approved = false
```

поэтому переход должен быть заблокирован.

После:

```text
approve plan
```

состояние содержит:

```text
plan_approved = true
```

Теперь:

```text
next
```

может выполнить:

```text
planning → execution
```

---

# Проверка незавершённой реализации

После перехода в:

```text
execution
```

сразу выполняем:

```text
next
```

Пока:

```text
implementation_completed = false
```

переход должен быть запрещён.

После команды:

```text
complete implementation
```

получаем:

```text
implementation_completed = true
```

Теперь разрешён:

```text
execution → validation
```

---

# Проверка завершения без валидации

На этапе:

```text
validation
```

попытка выполнить:

```text
next
```

при:

```text
validation_passed = false
```

должна быть заблокирована.

Сначала необходимо:

```text
pass validation
```

После этого:

```text
validation_passed = true
```

и разрешается:

```text
validation → done
```

---

# Pause / Resume

Контроль жизненного цикла также учитывает паузу.

Команда:

```text
pause
```

устанавливает:

```text
paused = true
```

Пока задача находится на паузе, переходы состояний запрещены.

Например:

```text
goto validation
```

должен быть заблокирован с требованием сначала продолжить задачу.

Для продолжения используется:

```text
resume
```

После этого:

```text
paused = false
```

и выполнение продолжается с того же состояния.

---

# Продолжение после перезапуска

Task State сохраняется в:

```text
task_state.json
```

Поэтому можно поставить задачу на паузу:

```text
pause
```

завершить программу:

```text
exit
```

и запустить её снова:

```powershell
py main.py
```

Состояние загружается из JSON.

Например, если программа была закрыта в:

```text
stage = execution
paused = true
```

после перезапуска эти данные должны сохраниться.

Команда:

```text
resume
```

продолжает работу с сохранённого этапа без повторного объяснения задачи.

---

# Полный корректный сценарий

Правильное прохождение жизненного цикла выглядит так:

```text
start Разработать Android-приложение для склада

        ↓

     planning

        ↓

approve plan

        ↓

      next

        ↓

    execution

        ↓

complete implementation

        ↓

      next

        ↓

   validation

        ↓

pass validation

        ↓

      next

        ↓

      done
```

Таким образом, каждый этап требует явного выполнения условия.

---

# Task State

Состояние хранится примерно в следующем виде:

```json
{
  "task": "Разработать Android-приложение для склада",
  "stage": "execution",
  "current_step": "Выполнить реализацию",
  "expected_action": "Завершить реализацию",
  "paused": false,
  "plan_approved": true,
  "implementation_completed": false,
  "validation_passed": false
}
```

Task State является источником истины для текущего жизненного цикла.

# Gemini и State Machine

Gemini получает текущее состояние задачи в каждом обычном запросе:

```text
TASK STATE
     +
USER REQUEST
     ↓
   GEMINI
```

В промпте модели явно описаны правила:

```text
нельзя делать реализацию
до утверждения плана

нельзя делать validation
до завершения реализации

нельзя делать done
до успешной validation

нельзя перепрыгивать состояния

нельзя продолжать paused-задачу
без resume
```

При этом Gemini не изменяет состояние самостоятельно.

Изменение выполняется только через State Machine.

Это разделяет:

```text
LLM
→ рассуждение и ответ

STATE MACHINE
→ контроль жизненного цикла
```

# Результат

В результате реализован ассистент с контролируемым жизненным циклом задачи.

Система умеет:

- хранить допустимые состояния;
- явно задавать разрешённые переходы;
- запрещать перепрыгивание этапов;
- проверять условия перед переходом;
- запрещать реализацию без утверждённого плана;
- запрещать validation до завершения реализации;
- запрещать `done` без успешной валидации;
- блокировать переходы во время паузы;
- объяснять причину блокировки;
- сохранять состояние в JSON;
- восстанавливать lifecycle после перезапуска;
- продолжать задачу с сохранённого этапа.

# Вывод

На предыдущих этапах Task State отвечал на вопрос:

```text
Где сейчас находится задача?
```

Теперь State Machine дополнительно отвечает:

```text
Куда задача имеет право перейти дальше?
```

И:

```text
Выполнены ли условия для этого перехода?
```

Получаем контролируемый процесс:

```text
STATE
  +
ALLOWED TRANSITIONS
  +
TRANSITION CONDITIONS
  +
PAUSE / RESUME
        ↓
CONTROLLED TASK LIFECYCLE
```

Ассистент больше не может просто перейти к следующему удобному этапу.

Каждый переход проверяется программно, а обязательные стадии жизненного цикла нельзя пропустить.
