# День 11 — Модель памяти агента

## Цель

Реализовать явную модель памяти AI-агента и разделить информацию на несколько независимых слоёв.

В агенте реализованы три типа памяти:

1. Short-Term Memory — краткосрочная память
2. Working Memory — рабочая память
3. Long-Term Memory — долговременная память

Каждый слой имеет своё назначение и хранится отдельно.

---

## Технологии

- Python
- Google Gemini API
- `google-genai`
- модель `gemini-3.5-flash-lite`
- JSON для хранения памяти
- CLI-интерфейс

---

# Архитектура памяти

Память агента разделена на три независимых слоя:

```text
                 ПАМЯТЬ АГЕНТА
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ↓              ↓              ↓
   SHORT-TERM       WORKING        LONG-TERM
      MEMORY         MEMORY          MEMORY
        │              │              │
 текущий диалог   текущая задача   постоянные
                                  данные/решения
```

Каждый тип памяти хранится отдельно:

```text
short_term_memory.json
working_memory.json
long_term_memory.json
```

---

# 1. Short-Term Memory

Short-Term Memory содержит текущий контекст разговора.

Обычные сообщения пользователя и ответы агента автоматически сохраняются именно в этот слой.

Например:

```text
Пользователь:
Какую архитектуру мы выбрали?

Ассистент:
Для текущего проекта используется MVVM.
```

Эти сообщения сохраняются в краткосрочной памяти.

В реализации установлен лимит:

```text
6 сообщений
```

Поэтому агент хранит только последние сообщения текущего разговора.

Схема:

```text
Сообщение пользователя
        ↓
      Gemini
        ↓
Ответ ассистента
        ↓
Short-Term Memory
```

### Назначение

Short-Term Memory используется для:

- текущего разговора;
- последних вопросов;
- последних ответов;
- локального контекста диалога.

---

# 2. Working Memory

Working Memory содержит информацию, относящуюся к текущей задаче или проекту.

В отличие от Short-Term Memory, данные сохраняются сюда явно.

Используется команда:

```text
remember work <ключ>=<значение>
```

Например:

```text
remember work project=Android-приложение для склада
```

```text
remember work min_android=12
```

```text
remember work architecture=MVVM
```

В результате рабочая память может выглядеть так:

```json
{
  "project": "Android-приложение для склада",
  "min_android": "12",
  "architecture": "MVVM"
}
```

### Назначение

Working Memory используется для:

- текущего проекта;
- требований;
- ограничений;
- параметров текущей задачи;
- временно принятых решений.

После завершения проекта эту память можно очистить.

---

# 3. Long-Term Memory

Long-Term Memory предназначена для информации, которая должна сохраняться независимо от текущей задачи.

Например:

- постоянные предпочтения;
- профиль пользователя;
- долгосрочные решения;
- знания, которые могут пригодиться в следующих задачах.

Данные сохраняются явно:

```text
remember long <ключ>=<значение>
```

Например:

```text
remember long preferred_language=Kotlin
```

В памяти появится:

```json
{
  "preferred_language": "Kotlin"
}
```

Эта информация не относится только к одному текущему проекту и может использоваться агентом позже.

---

# Явное управление памятью

Важная особенность реализации — агент не смешивает все данные в одной истории.

Для каждого типа информации явно определяется место хранения.

```text
Текущий разговор
        ↓
SHORT-TERM

Данные текущего проекта
        ↓
WORKING

Постоянные предпочтения и решения
        ↓
LONG-TERM
```

Рабочая и долговременная память изменяются только специальными командами.

Например:

```text
remember work min_android=12
```

явно означает:

```text
min_android
      ↓
WORKING MEMORY
```

А команда:

```text
remember long preferred_language=Kotlin
```

означает:

```text
preferred_language
      ↓
LONG-TERM MEMORY
```

Таким образом, можно точно контролировать, какие данные и в какой слой памяти попадают.

---

# Формирование запроса к Gemini

При обычном запросе агент объединяет информацию из всех трёх слоёв:

```text
LONG-TERM MEMORY
        +
WORKING MEMORY
        +
SHORT-TERM MEMORY
        +
НОВЫЙ ЗАПРОС
        ↓
      Gemini
```

Например, память содержит:

```text
LONG-TERM:
preferred_language = Kotlin

WORKING:
project = Android-приложение для склада
min_android = 12
architecture = MVVM

SHORT-TERM:
последние сообщения разговора
```

Пользователь спрашивает:

```text
На каком языке и с какой архитектурой
нам лучше делать текущий проект?
```

Агент может использовать информацию сразу из нескольких слоёв:

```text
Kotlin
+
MVVM
```

---

# Разница между слоями

| Тип памяти | Что хранит | Срок жизни | Как записывается |
|---|---|---|---|
| Short-Term | Текущий разговор | Короткий | Автоматически |
| Working | Данные текущей задачи | До завершения задачи | Явно |
| Long-Term | Постоянные предпочтения и решения | Долго | Явно |

---

# Проверка памяти

Для просмотра всех слоёв используется:

```text
memory
```

Пример:

```text
============================================================
МОДЕЛЬ ПАМЯТИ АГЕНТА
============================================================

1. SHORT-TERM MEMORY
------------------------------------------------------------
user: На каком языке будем писать?
assistant: Kotlin.

2. WORKING MEMORY
------------------------------------------------------------
{
  "project": "Android-приложение для склада",
  "min_android": "12",
  "architecture": "MVVM"
}

3. LONG-TERM MEMORY
------------------------------------------------------------
{
  "preferred_language": "Kotlin"
}
```

Также каждый слой можно посмотреть отдельно.

Краткосрочная память:

```text
short
```

Рабочая:

```text
work
```

Долговременная:

```text
long
```

---

# Очистка памяти

Каждый слой можно очищать независимо.

Очистить только текущий диалог:

```text
clear short
```

При этом Working и Long-Term Memory останутся.

Очистить данные текущей задачи:

```text
clear work
```

При этом долговременные предпочтения сохранятся.

Очистить долговременную память:

```text
clear long
```

Это позволяет управлять жизненным циклом разных типов информации.

---

# Эксперимент

Для проверки модели памяти можно сохранить:

```text
remember long preferred_language=Kotlin
```

Затем данные текущего проекта:

```text
remember work project=Android-приложение для склада
remember work min_android=12
remember work architecture=MVVM
```

После этого команда:

```text
memory
```

показывает, что информация действительно находится в разных слоях.

Далее задаём вопрос:

```text
На каком языке и с какой архитектурой
нам лучше делать текущий проект?
```

Агент использует одновременно:

```text
Long-Term Memory
preferred_language = Kotlin
```

и:

```text
Working Memory
architecture = MVVM
```

---

# Проверка жизненного цикла памяти

Дополнительно можно очистить краткосрочную и рабочую память:

```text
clear short
clear work
```

Но не очищать Long-Term Memory.

После этого:

```text
SHORT-TERM → пусто

WORKING → пусто

LONG-TERM →
preferred_language = Kotlin
```

Таким образом, информация текущего проекта исчезает, а долговременное предпочтение остаётся.

Это показывает различие жизненного цикла трёх слоёв памяти.

# Команды агента

```text
remember work <ключ>=<значение>
```

Сохранить значение в Working Memory.

```text
remember long <ключ>=<значение>
```

Сохранить значение в Long-Term Memory.

```text
memory
```

Показать все слои памяти.

```text
short
```

Показать Short-Term Memory.

```text
work
```

Показать Working Memory.

```text
long
```

Показать Long-Term Memory.

```text
clear short
```

Очистить Short-Term Memory.

```text
clear work
```

Очистить Working Memory.

```text
clear long
```

Очистить Long-Term Memory.

```text
stats
```

Показать статистику.

```text
help
```

Показать список команд.

```text
exit
```

Завершить работу программы.

# Результат

В результате реализован AI-агент с явной многоуровневой моделью памяти.

Агент умеет:

- хранить текущий диалог в Short-Term Memory;
- хранить данные текущей задачи в Working Memory;
- хранить постоянные данные в Long-Term Memory;
- явно выбирать слой при сохранении информации;
- использовать несколько типов памяти одновременно при формировании запроса;
- независимо просматривать каждый слой;
- независимо очищать каждый слой;
- сохранять память в отдельных JSON-файлах.

---

# Вывод

Одна общая история диалога не всегда является удобной моделью памяти агента.

Разделение памяти на слои позволяет учитывать жизненный цикл информации:

```text
SHORT-TERM
↓
Что происходит прямо сейчас?

WORKING
↓
Что важно для текущей задачи?

LONG-TERM
↓
Что важно сохранить надолго?
```

Такой подход делает память агента более управляемой и предсказуемой.

Агент явно понимает, какой контекст является временным, какой относится к текущей задаче, а какой должен сохраняться независимо от конкретного диалога.
