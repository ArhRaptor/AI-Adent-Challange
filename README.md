# День 28 — Локальная LLM + RAG

## Цель

Создать RAG-систему, полностью работающую локально, без обращения к облачным LLM API.

В рамках задания необходимо:

- использовать документы и принципы индексирования из Недели 6;
- создавать embeddings локально;
- выполнять retrieval по локальному индексу;
- генерировать ответы через локальную LLM;
- отображать найденные источники;
- оценить качество, скорость и стабильность;
- сравнить локальный подход с облачным RAG.

## Технологии

- **Python** — реализация RAG-пайплайна.
- **Ollama** — локальный inference runtime.
- **nomic-embed-text** — локальная модель embeddings.
- **qwen2.5-coder:0.5b** — локальная генеративная модель.
- **JSON** — хранение векторного индекса.
- **Cosine similarity** — оценка сходства вопроса и документов.
- **urllib.request** — HTTP-запросы к Ollama.

Дополнительные Python-библиотеки для текущей реализации не требуются.

## Архитектура

### Индексация

```text
Documents
    ↓
Read Files
    ↓
Fixed-Size Chunking
    ↓
Local Embeddings (Ollama)
    ↓
Metadata + Vectors
    ↓
indexes/index_local.json
```

### Ответ на вопрос

```text
User Question
    ↓
Local Query Embedding
    ↓
Cosine Similarity
    ↓
Top-4 Relevant Candidates
    ↓
Context Construction
    ↓
Local LLM (Ollama)
    ↓
Answer + Sources
```

Все операции embedding, retrieval и генерации выполняются локально.


## Локальная индексация

Для построения индекса используется:

```powershell
py index_local.py
```

Скрипт:

1. Читает документы из `documents/`.
2. Разбивает содержимое на chunks.
3. Получает embedding каждого chunk через Ollama.
4. Добавляет metadata.
5. Сохраняет результат в `indexes/index_local.json`.

### Chunking

Используются параметры:

```python
CHUNK_SIZE = 1200
CHUNK_OVERLAP = 200
```

Chunk overlap позволяет сохранять часть соседнего контекста при разбиении текста.

В Day 28 применяется fixed-size chunking. Структурный chunking из Недели 6 остаётся отдельной стратегией для дальнейших экспериментов.

### Metadata

Каждый chunk содержит:

```json
{
  "text": "...",
  "metadata": {
    "source": "documents/rag_notes.md",
    "title": "rag_notes.md",
    "section": null,
    "chunk_id": "rag_notes.md::local::0001",
    "strategy": "local-fixed"
  },
  "embedding": []
}
```

Поле `embedding` в настоящем индексе содержит числовой вектор, а не пустой массив.

Metadata позволяют определить происхождение найденного фрагмента.

## Почему нужен новый индекс

На Неделе 6 embeddings создавались через Gemini.

В Day 28 используется локальная модель `nomic-embed-text`.

Векторы разных embedding-моделей нельзя напрямую сравнивать как совместимые представления.

Поэтому документы индексируются повторно, уже локально.

Старые индексы сохраняются отдельно, а новый записывается в:

```text
indexes/index_local.json
```

## Retrieval

При каждом вопросе:

1. Ollama создаёт embedding вопроса.
2. Python сравнивает его с embeddings документов.
3. Вычисляется cosine similarity.
4. Результаты сортируются по убыванию similarity.
5. Выбираются четыре лучших chunk.

Настройка:

```python
TOP_K = 4
```

Cosine similarity:

\[
similarity(A,B)=\frac{A\cdot B}{\|A\|\|B\|}
\]

Поиск реализован перебором всех chunks. Для небольшого учебного индекса этого достаточно.

## Генерация ответа

Найденные chunks объединяются в контекст.

Локальная модель получает:

- системную инструкцию;
- контекст документов;
- вопрос пользователя.

Используется Ollama endpoint:

```text
http://localhost:11434/api/chat
```

System prompt требует отвечать на основании предоставленного контекста и не придумывать отсутствующие факты.

## Источники

После генерации приложение выводит найденные chunks.

Для каждого источника отображаются:

```text
source
chunk_id
similarity
```

Пример формата:

```text
ИСТОЧНИКИ:

[1] documents/rag_notes.md
    Chunk: rag_notes.md::local::0001
    Similarity: ...
```

Источники формируются программой из retrieval results.

**Ограничение:** текущая версия показывает найденные источники, но не доказывает автоматически, что каждое утверждение ответа действительно подтверждается ими.

## Измерение скорости

Для каждого вопроса измеряются:

```text
Retrieval Time
Generation Time
Total Time
```

Это позволяет отдельно оценивать время поиска и время генерации.

## Контрольные вопросы

### Тест 1 — Простой RAG

```text
Зачем используется overlap между chunks?
```

Проверяем, способен ли retrieval найти материал о chunking.

### Тест 2 — Сравнение подходов

```text
Чем fixed chunking отличается от structured chunking?
```

Проверяем ответ, требующий сравнения двух стратегий.

### Тест 3 — Другая предметная область

```text
Какую роль ViewModel выполняет в MVVM?
```

Проверяем поиск по Android-документации.

### Тест 4 — Нерелевантный вопрос

```text
Как приготовить борщ?
```

Проверяем поведение системы при отсутствии подходящего материала.

Текущая реализация использует Top-K без порога релевантности. Поэтому даже для нерелевантного вопроса она выбирает четыре лучших по similarity фрагмента.

Это ограничение необходимо учитывать при оценке качества.

## Local vs Cloud RAG

| Критерий | Local RAG | Cloud RAG |
|---|---|---|
| Embeddings | Ollama | Gemini |
| Generation | Ollama | Gemini |
| Retrieval | Локальный Python | Локальный Python |
| Интернет для inference | Не требуется | Требуется |
| Облачный API-ключ | Не требуется | Требуется |
| Стоимость LLM API | Нет | Зависит от тарифа |
| Качество | Требует тестирования | Требует тестирования |
| Скорость | Требует измерения | Требует измерения |
| Стабильность | Требует проверки | Требует проверки |

Для корректного сравнения необходимо использовать одинаковые контрольные вопросы и фиксировать ответы и время выполнения.

Поскольку embedding-модели различаются, результаты отражают качество всей системы, а не только генеративных моделей.

## Критерии оценки

**Качество:** соответствует ли ответ документам, содержит ли фактические ошибки, насколько релевантны найденные chunks.

**Скорость:** сколько времени занимает retrieval, генерация и полный запрос.

**Стабильность:** повторяются ли технические ошибки, успешно ли обрабатываются последовательные запросы, насколько устойчиво качество ответов.

## Ограничения реализации

- Используется компактная генеративная модель 0.5B.
- Нет автоматической проверки смыслового соответствия ответа источникам.
- Нет similarity threshold.
- Нет reranker.
- Индекс хранится в JSON.
- Retrieval выполняется полным перебором chunks.
- Локальная версия пока не содержит task memory из Day 25.
- Качество необходимо проверять на фактических результатах.

## Результат

Разработан RAG-пайплайн, использующий:

```text
Local Documents
+
Local Embeddings
+
Local Vector Index
+
Local Retrieval
+
Local LLM
```

Ключевое отличие от предыдущей версии RAG — отсутствие необходимости обращаться к облачному API для создания embeddings вопроса и генерации ответа.

Итоговая цепочка:

```text
Index Locally
→ Embed Locally
→ Retrieve Locally
→ Generate Locally
→ Display Sources
```

Day 28 демонстрирует архитектуру полностью локальной RAG-системы на базе Ollama.
