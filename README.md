# День 17 — Первый инструмент MCP

## Цель

Реализовать собственный MCP-инструмент, вызвать его из приложения и использовать полученный результат в AI-агенте.

На предыдущем этапе MCP-клиент только подключался к серверу и получал список доступных инструментов:

```text
CONNECT
   ↓
LIST TOOLS
   ↓
PRINT TOOLS
```

Теперь добавляется реальный вызов:

```text
CONNECT
   ↓
LIST TOOLS
   ↓
CALL TOOL
   ↓
GET RESULT
   ↓
GEMINI
   ↓
ANSWER
```

---

# Задача

В качестве внешнего источника данных используется учебный Mock API склада.

MCP-сервер предоставляет инструмент:

```text
get_product
```

который получает:

```text
product_id
```

и возвращает информацию о товаре.

Полученный через MCP результат передаётся AI-агенту, который формирует итоговый ответ пользователю.

# Mock API

Для учебного примера используется локальный набор товаров:

```python
PRODUCTS = {
    101: {
        "id": 101,
        "name": "Ноутбук Lenovo ThinkBook",
        "quantity": 7,
        "price": 85000,
        "warehouse": "Москва"
    },

    102: {
        "id": 102,
        "name": "Монитор Samsung 27",
        "quantity": 0,
        "price": 32000,
        "warehouse": "Москва"
    },

    103: {
        "id": 103,
        "name": "Клавиатура Logitech",
        "quantity": 24,
        "price": 6500,
        "warehouse": "Санкт-Петербург"
    }
}
```

Это имитирует внешний API склада.

В реальном проекте вместо локального словаря здесь может использоваться:

```text
REST API
CRM
ERP
Database
GitHub API
Яндекс.Трекер API
```

При этом MCP-интерфейс для агента может остаться тем же.

# Регистрация MCP Tool

Инструмент регистрируется на MCP-сервере:

```python
@mcp.tool(
    title="Получить товар",
    description=(
        "Возвращает информацию о товаре "
        "на складе по его ID."
    )
)
def get_product(product_id: int) -> dict:
```

После регистрации MCP-клиент может обнаружить инструмент через:

```python
await client.list_tools()
```

и вызвать его через:

```python
await client.call_tool(...)
```

---

# Входные параметры

Инструмент принимает:

```text
product_id
```

Тип:

```text
integer
```

Сигнатура Python:

```python
def get_product(product_id: int) -> dict:
```

MCP SDK использует описание функции и её параметры для формирования схемы инструмента.

Клиент может получить эту схему через `list_tools()`.

---

# Результат инструмента

Если товар найден, инструмент возвращает структуру:

```json
{
  "success": true,
  "product": {
    "id": 101,
    "name": "Ноутбук Lenovo ThinkBook",
    "quantity": 7,
    "price": 85000,
    "warehouse": "Москва"
  }
}
```

Если товара нет:

```json
{
  "success": false,
  "error": "Товар не найден",
  "product_id": 999
}
```

Таким образом инструмент возвращает структурированный результат, который приложение может использовать дальше.

---

# Подключение MCP Client

Клиент подключается к локальному MCP-серверу через stdio.

Параметры сервера:

```python
server = StdioServerParameters(
    command="py",
    args=["mcp_server.py"]
)
```

После этого устанавливается соединение:

```python
async with Client(server) as client:
```

Клиент запускает локальный MCP-сервер и может обращаться к опубликованным им инструментам.

---

# Получение списка инструментов

Перед вызовом инструмента клиент выполняет:

```python
tools_result = await client.list_tools()
```

Это позволяет увидеть доступные MCP Tools.

Для каждого инструмента выводятся:

```text
Name
Description
Input schema
```

В нашем случае сервер предоставляет:

```text
get_product
```

# Первый вызов MCP Tool

Главное отличие от Дня 16 — использование:

```python
result = await client.call_tool(
    "get_product",
    {
        "product_id": product_id
    }
)
```

Здесь:

```text
get_product
```

— имя MCP-инструмента,

а:

```python
{
    "product_id": product_id
}
```

— его входные аргументы.

# Полный путь вызова

Например пользователь вводит:

```text
101
```

Далее происходит:

```text
101
 │
 ↓
MCP Client
 │
 ↓
call_tool(
    "get_product",
    {"product_id": 101}
)
 │
 ↓
MCP Server
 │
 ↓
get_product(101)
 │
 ↓
Mock API
 │
 ↓
PRODUCTS[101]
 │
 ↓
MCP Result
```

Полученные данные возвращаются обратно клиенту.

---

# Обработка результата MCP

После вызова:

```python
result = await client.call_tool(...)
```

приложение получает `CallToolResult`.

В реализации сначала проверяется структурированный результат:

```python
result.structured_content
```

Если его нет, используется fallback через:

```python
result.content
```

и:

```python
TextContent
```

Это позволяет получить данные инструмента и подготовить их для дальнейшей обработки.

---

# Обработка ошибки MCP

Также проверяется:

```python
result.is_error
```

Если MCP сообщает об ошибке выполнения инструмента, приложение не передаёт некорректный результат дальше как успешный.

---

# Передача результата агенту

После получения данных они передаются Gemini:

```python
answer = agent.ask_gemini(
    user_message,
    tool_data
)
```

В prompt попадают:

```text
USER MESSAGE
      +
MCP TOOL RESULT
      ↓
    GEMINI
      ↓
FINAL ANSWER
```

То есть Gemini получает данные не из собственной памяти, а от MCP-инструмента.

---

# Использование результата

В prompt агенту явно указано:

```text
Не придумывай данные о товаре.

Используй результат MCP
как источник данных.
```

Если товар найден, агент использует:

```text
name
quantity
price
warehouse
```

Если:

```text
quantity = 0
```

агент должен сообщить, что товара сейчас нет в наличии.

Если:

```text
success = false
```

агент сообщает, что товар не найден.

# Разделение ответственности

В архитектуре каждый компонент отвечает за свою часть.

### Mock API

```text
Хранит данные
```

### MCP Tool

```text
Предоставляет стандартный интерфейс
для получения данных
```

### MCP Server

```text
Публикует инструменты
```

### MCP Client

```text
Обнаруживает и вызывает инструменты
```

### Gemini

```text
Интерпретирует результат инструмента
и формирует ответ пользователю
```

Получается:

```text
DATA
 ↓
TOOL
 ↓
MCP
 ↓
AGENT
 ↓
USER
```

# Важное ограничение текущей версии

В текущей реализации приложение само знает, какой MCP-инструмент необходимо вызвать:

```python
client.call_tool(
    "get_product",
    ...
)
```

То есть сейчас схема такая:

```text
Application
     ↓
выбирает get_product
     ↓
MCP
     ↓
Tool
     ↓
Gemini
```

LLM пока самостоятельно не выбирает инструмент.

Более продвинутая архитектура будет выглядеть так:

```text
User
 ↓
Gemini
 ↓
выбирает нужный Tool
 ↓
MCP Client
 ↓
MCP Server
 ↓
Tool
 ↓
Result
 ↓
Gemini
 ↓
Final Answer
```

Это следующий уровень развития AI-агента.
