# День 14 — Инварианты и ограничения состояния

## Цель

Добавить в AI-ассистента формализованные инварианты — правила и ограничения, которые агент не имеет права нарушать при выполнении задачи.

Примеры инвариантов:

- выбранная архитектура;
- язык разработки;
- используемый UI-стек;
- ограничения платформы;
- технические решения;
- бизнес-правила.

Инварианты должны храниться отдельно от диалога и Task State.

При каждом запросе агент должен учитывать их и отказываться предлагать решения, которые им противоречат.

---

## Технологии

- Python
- Google Gemini API
- `google-genai`
- модель `gemini-3.5-flash-lite`
- JSON
- Task State Machine
- Invariant Guard
- CLI-интерфейс

# Архитектура

В предыдущем задании был реализован Task State Machine:

```text
planning
    ↓
execution
    ↓
validation
    ↓
done
```

Теперь поверх состояния задачи добавлен отдельный слой обязательных ограничений:

```text
TASK STATE
→ где находится задача

INVARIANTS
→ какие правила нельзя нарушать
```

Общая схема:

```text
                 USER REQUEST
                      │
                      ↓
              INVARIANT GUARD
                      │
               есть конфликт?
                 /         \
               ДА           НЕТ
               │             │
               ↓             ↓
             BLOCK         GEMINI
                             │
                    TASK STATE
                         +
                    INVARIANTS
                             │
                             ↓
                           ANSWER
```

---

# Что такое инвариант

Инвариант — это правило, которое должно оставаться истинным во время выполнения задачи.

Например:

```text
architecture = MVVM
language = Kotlin
ui = Jetpack Compose
min_android = 12
```

Если архитектура проекта зафиксирована как:

```text
MVVM
```

обычный запрос:

```text
Давай вместо MVVM используем MVP.
```

не должен автоматически менять принятое техническое решение.

Такой запрос конфликтует с существующим инвариантом.

---

# Отделение инвариантов от других данных

В агенте используются разные типы состояния:

```text
DIALOG
→ что пользователь сказал

MEMORY
→ что агент знает

TASK STATE
→ где находится задача

INVARIANTS
→ что нельзя нарушать
```

Инварианты специально не хранятся в обычной истории диалога.

Они сохраняются отдельно:

```text
invariants.json
```

Например:

```json
{
  "architecture": "MVVM",
  "language": "Kotlin",
  "ui": "Jetpack Compose",
  "min_android": "12"
}
```

---

# InvariantManager

Для управления ограничениями реализован отдельный класс:

```text
InvariantManager
```

Он отвечает за:

- загрузку инвариантов;
- сохранение;
- добавление;
- изменение;
- удаление;
- просмотр;
- очистку;
- проверку конфликтов.

Это отделяет правила системы от логики Task State Machine и от обычного диалога.

---

# Добавление инвариантов

Инвариант добавляется специальной командой:

```text
invariant <ключ>=<значение>
```

Например:

```text
invariant architecture=MVVM
```

```text
invariant language=Kotlin
```

```text
invariant ui=Jetpack Compose
```

```text
invariant min_android=12
```

После этого:

```text
invariants
```

показывает:

```text
============================================================
INVARIANTS
============================================================

architecture = MVVM
language = Kotlin
ui = Jetpack Compose
min_android = 12
```

---

# Два уровня защиты

В реализации используется два уровня проверки ограничений.

## Уровень 1 — Python Guard

Перед отправкой запроса Gemini выполняется локальная проверка:

```text
USER REQUEST
      ↓
check_conflicts()
      ↓
есть очевидный конфликт?
```

Если конфликт найден, запрос блокируется ещё до обращения к Gemini.

Например:

```text
architecture = MVVM
```

Пользователь:

```text
Давай сделаем архитектуру MVP.
```

Результат:

```text
КОНФЛИКТ С ИНВАРИАНТАМИ

architecture=MVVM конфликтует с MVP
```

Gemini в этом случае не вызывается.

---

## Уровень 2 — Gemini

Если Python Guard не обнаружил явного конфликта, запрос передаётся Gemini.

Но вместе с запросом модель получает полный список инвариантов:

```text
TASK STATE
+
INVARIANTS
+
USER REQUEST
```

В промпте явно указано:

```text
1. Проверить запрос на конфликт с инвариантами.
2. Не предлагать решение, нарушающее инвариант.
3. Объяснить найденный конфликт.
4. По возможности предложить допустимую альтернативу.
5. Не изменять инварианты самостоятельно.
```

Таким образом, модель тоже должна учитывать ограничения при формировании решения.

---

# Почему используются два уровня

Если полагаться только на промпт:

```text
"Пожалуйста, соблюдай ограничения"
```

контроль полностью передаётся LLM.

В реализации используется дополнительный детерминированный слой:

```text
          REQUEST
             ↓
       PYTHON GUARD
          /     \
         /       \
   CONFLICT      OK
       ↓          ↓
     BLOCK      GEMINI
                  ↓
              INVARIANTS
                  ↓
                ANSWER
```

Преимущества:

- очевидные нарушения блокируются кодом;
- запрещённый запрос не отправляется модели;
- поведение становится более предсказуемым;
- на заблокированный запрос не расходуются токены Gemini;
- модель дополнительно учитывает остальные ограничения.

# Проверка нормального запроса

Создаём задачу:

```text
start Разработать Android-приложение для склада
```

Добавляем ограничения:

```text
invariant architecture=MVVM
invariant language=Kotlin
invariant ui=Jetpack Compose
invariant min_android=12
```

Теперь задаём:

```text
Предложи архитектуру экрана списка товаров.
```

Запрос не нарушает инварианты.

Поэтому он передаётся Gemini вместе с ограничениями:

```text
architecture = MVVM
language = Kotlin
ui = Jetpack Compose
min_android = 12
```

Агент должен сформировать решение внутри этих рамок.

---

# Проверка конфликта архитектуры

Инвариант:

```text
architecture = MVVM
```

Запрос:

```text
Давай откажемся от MVVM и сделаем архитектуру MVP.
```

Python Guard обнаруживает конфликт:

```text
architecture=MVVM конфликтует с MVP
```

Агент отказывается выполнять запрос, поскольку он нарушает зафиксированное техническое решение.

---

# Проверка нескольких конфликтов

Инварианты:

```text
language = Kotlin
ui = Jetpack Compose
```

Запрос:

```text
Перепиши приложение на Java
и используй XML вместо Jetpack Compose.
```

В запросе одновременно нарушаются два правила.

Ожидаемый результат:

```text
КОНФЛИКТ С ИНВАРИАНТАМИ

- language=Kotlin конфликтует с Java
- ui=Jetpack Compose конфликтует с XML UI
```

Агент объясняет причину отказа и не отправляет запрещённое решение Gemini.

---

# Явное изменение инварианта

Инварианты можно изменять.

Но изменение должно происходить явно через управляющую команду.

Например:

```text
invariant architecture=MVP
```

После этого:

```text
invariants
```

покажет:

```text
architecture = MVP
```

Таким образом:

```text
Обычный запрос:

"Давай используй MVP"
        ↓
не изменяет invariant
```

Но:

```text
Управляющая команда:

invariant architecture=MVP
        ↓
явно изменяет invariant
```

Это позволяет отделить разговор пользователя от изменения системных ограничений.

---

# Удаление инварианта

Удалить конкретное ограничение:

```text
remove invariant <ключ>
```

Например:

```text
remove invariant architecture
```

После этого правило архитектуры больше не является обязательным.

---

# Очистка инвариантов

Удалить все ограничения:

```text
clear invariants
```

Это очищает:

```text
invariants.json
```

но не сбрасывает Task State.

---

# Инварианты и Task State

Task State Machine и Invariants решают разные задачи.

Task State:

```text
task
stage
current_step
expected_action
paused
```

отвечает на вопрос:

```text
Где мы сейчас в процессе?
```

Invariants:

```text
architecture
language
ui
min_android
business_rules
...
```

отвечают:

```text
В каких рамках мы должны работать?
```

Их можно использовать одновременно:

```text
TASK:
Android-приложение для склада

STAGE:
execution

CURRENT STEP:
Реализовать экран списка товаров

INVARIANTS:
architecture = MVVM
language = Kotlin
ui = Jetpack Compose
min_android = 12
```

Агент получает одновременно состояние процесса и технические ограничения.

# Ограничение учебной реализации

Локальный Python Guard в текущей версии проверяет заранее определённые технические конфликты.

Например:

```text
MVVM ↔ MVP / MVC
Kotlin ↔ Java
Jetpack Compose ↔ XML UI
```

Это сделано специально, чтобы механизм детерминированной проверки был хорошо виден.

Более сложные или произвольные инварианты всё равно передаются Gemini.

В production-системе проверку можно развить в универсальный rule engine со структурированными типами правил и отдельными валидаторами.

В результате реализован AI-ассистент, который работает внутри формализованных ограничений.

Агент умеет:

- хранить инварианты отдельно от диалога;
- сохранять их в JSON;
- передавать их Gemini при каждом запросе;
- проверять очевидные конфликты до обращения к LLM;
- блокировать запрещённые решения;
- объяснять причину отказа;
- обнаруживать несколько конфликтов;
- явно изменять инварианты;
- удалять ограничения;
- использовать Invariants совместно с Task State Machine.

# Вывод

Task State определяет:

```text
Где находится задача?
```

Memory определяет:

```text
Что агент знает?
```

Invariants определяют:

```text
Что агент не имеет права нарушать?
```

В результате решение формируется не только из запроса пользователя:

```text
USER REQUEST
```

а внутри заданных рамок:

```text
TASK STATE
     +
INVARIANTS
     +
USER REQUEST
     ↓
VALIDATION
     ↓
ALLOWED / BLOCKED
```

Такой подход делает поведение AI-агента более контролируемым и предсказуемым: ранее принятые технические решения, ограничения стека и бизнес-правила не могут быть случайно отменены обычным сообщением пользователя.
