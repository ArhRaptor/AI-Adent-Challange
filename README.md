# День 9 — Управление контекстом: сжатие истории

## Цель

Реализовать механизм управления контекстом агента, чтобы длинная история диалога не передавалась в LLM целиком при каждом новом запросе.

Агент должен:

- хранить последние сообщения без изменений;
- старые сообщения заменять кратким `summary`;
- хранить `summary` отдельно;
- использовать `summary` вместе с последними сообщениями при следующих запросах;
- уменьшать расход токенов при длинном диалоге.

---

## Используемые технологии

- Python
- Google Gemini API
- `google-genai`
- модель `gemini-3.5-flash-lite`
- JSON для хранения последних сообщений
- TXT для хранения summary

---

## Как работает агент

История диалога разделяется на две части:

```text
Старые сообщения
       ↓
    SUMMARY
       +
Последние сообщения
       +
Новый запрос пользователя
       ↓
     Gemini
```

В текущей реализации:

```text
Последних сообщений без сжатия: 6
Количество сообщений для одного сжатия: 10
```

Последние 6 сообщений сохраняются полностью, потому что в них находится наиболее актуальный контекст разговора.

Более старые сообщения периодически передаются Gemini для создания краткого `summary`.

После этого исходные старые сообщения удаляются из текущей истории, а вместо них при следующих запросах используется summary.

---

## Хранение контекста

Используются два файла:

### `history.json`

Содержит последние сообщения диалога без изменений.

### `summary.txt`

Содержит краткое описание старой части разговора.

Таким образом, агенту не требуется каждый раз отправлять модели всю историю диалога.

---

## Проверка работы

Для тестирования был проведён диалог о коте Барсике.

В процессе разговора агент запоминал информацию о коте и продолжал использовать предыдущие сообщения как контекст.

До сжатия количество входных токенов постепенно увеличивалось:

```text
19
120
193
283
394
510
667
838
```

Это показывает, что с каждым новым сообщением размер передаваемой истории увеличивается.

После накопления достаточного количества сообщений автоматически запустилось сжатие:

```text
============================================================
СЖАТИЕ ИСТОРИИ
============================================================
Сообщений для сжатия: 10

Создаём summary...
```

Результат:

```text
Входных токенов:   616
Токенов summary:   64
Thinking tokens:   0
Всего токенов API: 680
```

После создания summary:

```text
Старые сообщения заменены summary.
Сообщений осталось без сжатия: 6
```

То есть 10 старых сообщений были заменены значительно более коротким summary, а 6 последних сообщений сохранились полностью.

---

## Сравнение количества токенов

Перед сжатием последний запрос использовал:

```text
838 входных токенов
```

После сжатия следующий запрос использовал:

```text
579 входных токенов
```

Разница:

```text
838 - 579 = 259 токенов
```

Снижение относительно значения перед сжатием составляет примерно:

```text
31%
```

При дальнейшем увеличении диалога эффект от сжатия становится более заметным, поскольку старые сообщения больше не требуется постоянно передавать модели полностью.

Важно: это не идеально контролируемый benchmark, поскольку сами запросы до и после сжатия отличаются. Эти значения показывают практическое изменение размера контекста в ходе реального диалога.

---

## Стоимость сжатия

Создание summary само по себе является отдельным запросом к Gemini и также расходует токены.

В эксперименте создание summary потребовало:

```text
616 входных токенов
64 токена ответа
680 токенов API всего
```

Поэтому сжатие имеет дополнительную стоимость в момент создания summary.

Однако созданный summary затем используется повторно вместо большого количества старых сообщений. На длинных диалогах это позволяет уменьшить размер последующих запросов.

---

## Качество после сжатия

После сжатия агент продолжил понимать контекст разговора.

Например, после удаления старых сообщений из обычной истории агент всё ещё знал:

- что кота зовут Барсик;
- что обсуждалось его плохое поведение;
- что он разбил кружку и испортил тапки;
- что обсуждалась кастрация;
- общий смысл предыдущего разговора.

Это возможно благодаря тому, что основные факты из старых сообщений были сохранены в `summary`.

При этом компрессия имеет недостаток: summary является сокращённым представлением разговора, поэтому мелкие детали потенциально могут быть потеряны.

## Команды агента

В CLI реализованы команды:

```text
help
```

Показать доступные команды.

```text
stats
```

Показать статистику текущего контекста и последнего запроса.

```text
summary
```

Показать сохранённый summary.

```text
clear
```

Очистить историю и summary.

```text

```

Завершить работу программы.

## Результат

В результате был реализован агент с компрессией истории.

Агент:

- сохраняет контекст между сообщениями;
- хранит последние сообщения полностью;
- автоматически сжимает старую историю;
- сохраняет summary отдельно;
- использует summary в последующих запросах;
- показывает фактическое количество токенов;
- уменьшает размер контекста после сжатия;
- продолжает помнить основные факты старого диалога.

## Вывод

Полная передача истории удобна для коротких диалогов, но количество входных токенов постоянно растёт.

Сжатие позволяет заменить старую часть разговора коротким summary:

```text
Полная история
      ↓
Старые сообщения → Summary
Последние сообщения → без изменений
```

В проведённом тесте перед сжатием использовалось 838 входных токенов, а в следующем запросе после сжатия — 579.

При этом агент сохранил основной контекст разговора.

Таким образом, компрессия истории позволяет экономить токены и помогает агенту работать с длинными диалогами, но создаёт компромисс между экономией контекста и сохранением всех деталей разговора.
